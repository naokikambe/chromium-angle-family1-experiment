# Automation operations

## Scheduled monitor

`.github/workflows/watch-chrome-stable.yml` checks every six hours on `main`. A newly published Stable version is fetched from its exact Chromium version tag and checked against `chrome/VERSION` and `DEPS`. The workflow resolves a known version's exact baseline binding or the unique defaults for an unregistered version, then applies the selected patch, runs focused tests, verifies the pinned Xcode/SDK recipe, builds ANGLE, and stores a verified candidate. Normal runs need no local machine, login, response, or device.

The workflow has `contents:read` and `actions:read`; source checkout credentials are not persisted. It creates no commit, catalog change, PR, issue, tag, release, notification, or device evidence. It serializes monitor runs. Normal monitoring compares exact four-part versions against `last_successful_version`, falling back to `monitor_start_version` only when there has been no formal success. `last_detected_version` remains detection history and does not set the comparison boundary.

## State and recovery

The rolling state and version index are JSON in the `stable-monitor-state` Actions artifact. Its exact archive member is `stable-monitor-state.json`; it is refreshed at the end of each monitor run and retained for 90 days. The candidate package is a separate Actions artifact, also retained for 90 days. State schema v1 is accepted and migrated to v2 without removing records or reducing `last_detected_version`. The migration derives `last_successful_version` only from existing `CI_BUILD_SUCCEEDED` records; an empty success history leaves it unset and keeps the configured start baseline separate. `success_index` and `candidate_outcomes` preserve the watermark, successful artifact metadata, source pins, and each version's attempted fingerprints when the 1,000-record history list is trimmed. Success summaries retain platform and architecture, and local match/fetch consults that persistent index as well as recent records. Older summaries without exact platform or architecture metadata are not guessed into a match; a retained detailed success record can refresh those fields during migration.

Before source resolution or any candidate build, the monitor uploads `stable-monitor-checkpoint-<run-id>` with the same `stable-monitor-state.json` member. After the exact Chromium/ANGLE pins and current patch/recipe inputs are recorded, it uploads `stable-monitor-resolved-checkpoint-<run-id>` before building. Source resolution and build steps require the pre-build checkpoint; the build also requires the resolved-input checkpoint. If a completed run has no final state but has a valid checkpoint, the reader restores the newest checkpoint and changes its pending attempt to `CI_BUILD_INTERRUPTED`, preserving its fingerprint and pins. It does not advance the success watermark. Recovered attempts are not duplicated with the same fingerprint. A checkpoint expiry, malformed archive, or invalid schema fails closed.

The build step can only write `CI_BUILD_SUCCEEDED_PENDING_STATE` after the candidate artifact upload, artifact/run match, and manifest checks succeed. The `last_successful_version` watermark is promoted only when the next monitor reads the final `stable-monitor-state` artifact that contains that pending record. If final state publication fails, the reader falls back to a checkpoint and treats the run as interrupted. A final state artifact that expires or goes missing causes the existing `state-lost` stop/recovery path; it is not interpreted as a failed build or an empty success history.

If the latest run has neither final state nor checkpoint, the reader can use the previous valid state because that run was gated from building. It continues across runs without either artifact until it finds a valid final state or checkpoint. If the recorded artifact is expired, unreadable, or all saved states are missing, normal monitoring stops with `state-lost`; it never silently returns to the 156 baseline.

The first run can initialize `monitor_start_version=156.0.8078.48` when the workflow has no prior completed runs and no state artifacts. This is a starting boundary, not a claim that Chrome 156 succeeded. It does not depend on the workflow file’s commit date, so PR review delay cannot close an initial time window.

For explicit recovery, manually dispatch `watch-chrome-stable.yml` with `operation=recover_state`. The recovery job does not resolve source or build ANGLE. It restores the latest retained state/checkpoint and writes an audit record. If no state can be recovered, the owner must enter the exact last processed Chrome version and a generic lowercase reason slug such as `owner-confirmed-history-loss`; do not enter personal, device, or local details. The job writes a `STATE_RECOVERY_AUDIT` record and saves the state artifact without building. That version becomes both the start boundary and detection history; it is not recorded as a successful build. State-recovery dispatch requires separate owner approval.

Local `match` and `fetch` use the same final state artifact contract and require a successful, unexpired indexed record whose live artifact metadata, run ID, build key, exact Chrome version, architecture, manifest, and hashes agree.

Two manual operations handle different cases:

- `operation=reacquire_expired_artifact` with `reacquire_version` selects a prior successful exact-version record whose artifact is no longer available. It uses that success record's Chromium and ANGLE pins. It does not claim bit-for-bit restoration of expired bytes.
- `operation=retry_failed_version` with `retry_failed_version` selects the latest failed or interrupted attempt for the exact version. It creates a new run record and never rolls back `last_detected_version` or `last_successful_version`. The new run records the failed run ID and stage, exact source pins, patch and recipe identifiers/hashes, selection mode, workflow revision, build key, and effective-input fingerprint. When prior source pins exist, the exact Chromium tag must resolve to those same pins or the retry stops. If no source pins were recorded because source resolution did not finish, the dispatch also requires `confirm_unpinned_retry=true`; the new run then records that it resolved the exact version tag afresh.

The explicit retry and re-acquire operations remain separate from normal monitoring. For a normal Stable candidate, the fingerprint is computed before source resolution by reading every tracked relevant workflow, build/verification, source/catalog/recipe, patch, license, and executed policy-test input. It includes the exact Chrome version and file bytes, excludes documentation and workflow commit IDs, and is never produced if any required file cannot be inspected. A same-version source-pin change is separately recorded and rejected.

If a version has failed with the same fingerprint, the scheduled run keeps the candidate and failure reason, reports `ACTION_REQUIRED`, and starts no build. If relevant inputs change, that new fingerprint receives one automatic attempt; a failure under that fingerprint is then suppressed. Previously attempted fingerprints stay suppressed even if files later revert to those bytes. A failure or interruption from schema v1 has no comparable fingerprint and is held for explicit attention rather than automatically retried just because the state migrated. An active or incomplete prior attempt also blocks another run. A newer fully rolled-out Stable is selected independently of an older failed version.

On the first scheduled run after this change reaches `main`, the monitor compares the latest fully served Stable with the derived last-successful watermark. If that release is the same version as a legacy failed/interrupted record without a fingerprint, it is retained as `ACTION_REQUIRED` with automatic retry suppressed. If a newer Stable is available, that newer version can be attempted without being blocked by the old failure. If no successful record exists, the monitor uses the separate start baseline, never `last_detected_version`, for comparison.

The Chrome 158 failure recorded in [`158-candidate-retry-plan.md`](158-candidate-retry-plan.md) is historical. PR #3 later merged the artifact redirect fix into `main`; the old run and artifact identifiers do not establish current retry eligibility or availability. Before any retry, inspect the current state and exact source pins using the plan. A retry is a new manual workflow dispatch and requires separate owner approval. Do not rerun the historical failed run as a substitute for an audited retry.

## PR validation and activation

`validate-pr.yml` runs read-only catalog, unit, synthetic, privacy, and safe-push fixture checks against the proposed merge with `main`. For same-repository PRs, success gates a two-version matrix of full ANGLE builds (156 and 158), each with the same pinned toolchain and shared build/verification entrypoint as the monitor. Inspect the synthetic job and both matrix jobs. A skipped build or a pass on an older head/base is not current full-build acceptance. Fork PRs receive only the synthetic checks.

PR builds do not trigger the monitor, update state/index, or retry the recorded failed version. Their outputs are marked PR-only, retain merge provenance, and expire in seven days. The workflow has no push, schedule, or dispatch trigger. A PR update automatically starts these checks and can consume two macOS build jobs, each up to 240 minutes. The recorded 45–150-minute estimate per 158 build remains unmeasured. The branch's PR does not activate the scheduled monitor.

The schedule becomes active only after separately approved integration into the default branch. A squash merge is the proposed linear-history method. Publishing to `main` can start the next six-hour monitor run. That run selects the newest fully rolled-out Mac Stable above the last successful version (or the explicit start baseline when no success exists). A legacy failed version that is still newest is retained as `ACTION_REQUIRED` because it has no fingerprint; a newer version can be attempted. State this bounded possible build in the reviewed PR and integration approval. The `reproduce-baseline.yml` workflow and all manual dispatches remain owner-approved actions.

The maintenance migration removed obsolete workflow source files and their dedicated helpers. It did not disable workflows registered from `main` or delete old runs, artifacts, or other-branch copies. Repository administration, workflow retention settings, and the external publication guard are unchanged. See the [publication plan](main-publication-plan.md) and [build retention](build-and-artifacts.md).
