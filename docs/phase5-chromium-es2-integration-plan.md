# Phase 5 Chromium ES2 integration boundary

This note records a source-level investigation for a narrowly scoped WebGL 1 experiment using the pinned Chromium 1689422 source and its DEPS-pinned ANGLE. It is a proposal for review, not an implementation or runtime result. The experiment must report actual GLES capabilities and must not relabel ES2 as ES3, synthesize a GLES version string, or count SwiftShader or another backend as Metal success.

## ANGLE capability boundary

At ANGLE revision `8efd15f71c27cd0bc2a9cf0074d77e899ca9c448`, `DisplayMtl::getMaxSupportedESVersion()` in `src/libANGLE/renderer/metal/DisplayMtl.mm` returns `mtl::kMaxSupportedGLVersion` when `supportsEitherGPUFamily(4, 1)` succeeds, otherwise ES 2.0. The arguments are the iOS GPU family and Mac GPU family. The concrete query depends on the compile-time deployment target: `mtl_utils.mm` maps Mac family 1 to `MTLGPUFamilyMac1` when targeting before macOS 13, and to `MTLGPUFamilyMac2` for macOS 13 or later. The current ANGLE candidate adds an exact-value runtime opt-in that queries native Mac1 and excludes native Mac2 on macOS, restoring the original family predicate for that narrowly selected device; it removes the separate ES2 ceiling. The candidate preserves the old mapping by default and leaves Catalyst and Family 2 paths unchanged. This is a capability-query experiment only: it does not establish that every advertised ES3 feature, limit, shader path, or workload works on Mac1.

The native-family candidate must first be evaluated through its actual ANGLE build and context/draw checks. Its use does not justify treating Mac1 as generally ES3-conformant. The ANGLE source exposes `requireGpuFamily2` as a separate initialization gate; disabling that gate does not establish support for all other Metal features. A WebGL 1-only experiment remains the narrower acceptance target while ES3 caps, feature initialization, shader-language selection, and workload behavior remain unproven.

## Chromium fallback boundary

At Chromium revision `82303c21a18acdc256c6264cd2ed0e1588df99d4`, `ui/gl/gl_features.cc` defines `kFallbackToSWIfGLES3NotSupported` only for Windows and ChromeOS. `ShouldFallbackToSWIfGLES3NotSupported()` returns `true` unconditionally on other platforms, including macOS, so disabling that feature through a feature-list flag is not available on macOS in this revision. `gpu/config/gpu_info_collector.cc` uses that result to set `GLContextAttribs::allow_es_version_fallback` to its inverse. In `ui/gl/gl_context_egl.cc`, when a selected EGL config lacks `EGL_OPENGL_ES3_BIT`, that attribute permits the request to be reduced to ES2; with it disabled, context initialization reports unsupported GLES3 and fails.

The held review proposal in `patches/phase5-chromium-family1-es2-info-context.patch` changes only `gpu/config/gpu_info_collector.cc`. On macOS, GPU information collection may use the existing truthful ES3-to-ES2 retry only when `ANGLE_PHASE5_ENABLE_METAL_FAMILY1` is exactly `1` and the command line selects `--use-gl=angle`, `--use-angle=metal`, `--use-dynamic-angle`, and exactly `--disable-angle-features=requireGpuFamily2`. Other platforms and every missing or different opt-in retain the baseline behavior. This does not introduce a new switch, change the global fallback feature, change EGL's requested version or response, alter ANGLE's maximum ES version, or permit WebGL2 to masquerade as WebGL1. It is an alternative to the original startup failure at the GPU-information context, not a substitute for ANGLE's current native-family candidate. Keep it uncompiled and held until the native-family candidate's actual build and context results show that this Chromium fallback is still needed. The existing EGL path must create a real ES2 context and report its actual version; a failed ES2 creation still fails.

This is an uncompiled proposal, not a ready app or a sufficient integration fix. `gpu_info_collector.cc` uses `allow_es_version_fallback` only for its offscreen context used to collect GL strings, version, extensions, and related GPU information. `GLContextEGL` performs the real ES3-to-ES2 downgrade only when that context's config lacks the ES3 renderable bit (or follows its separate no-config context retry); it does not rewrite the GL version returned by the driver. This proposal therefore addresses initial GPU-information collection only. `gpu_util.cc` derives accelerated WebGL and WebGL2 status from software use and blocklist results, not directly from a successful ES3 context in the shown path, so an ES2 info context must not be read as proof that WebGL2 is available or unavailable. `gles2_cmd_decoder_passthrough.cc` has a separately created lazy shared context that permits version fallback, and it contains ES3-only query handling for contexts identified as WebGL2/ES3; these points do not establish that the main WebGL service context or the compositor can operate at ES2. The required client-context, decoder, shared-image/Skia, and compositor behavior remains unresolved and needs source and runtime audit. Before any build, verify these switches and the opt-in environment reach the initial GPU process. A source-built app also needs a reviewed unsigned-build and first-sign procedure: the snapshot-only signing adapter must not be pointed at a source build by fabricating its snapshot identity. No signed existing app may be patched or re-signed.

Acceptance requires actual ES2/WebGL1 context creation, shader compile/link, draw/readback, stable GPU process lifetime, and the custom ANGLE/Metal libraries tied to that same GPU PID during the draw. Repeat normal Keychain, three independent page/profile checks, cookie persistence and normal restart on the assembled source-build candidate. WebGL2 and any GLES3-dependent features remain unaccepted unless independently demonstrated. KOOV's start gate remains closed until these checks pass.

## Build and acceptance constraints

The checked-in `phase5-chromium-url-diagnostic.yml` workflow can build a full Chromium app with `autoninja chrome` on `macos-15-intel`; its current defaults point to a different Chromium and ANGLE revision, and it applies URL-diagnostic and Xcode-compatibility patches. It uses pinned depot_tools, a 280-minute build-step limit, and a 360-minute job limit. Its GN settings include a non-component, unbranded, non-official x64 build, system Xcode, disabled Clang modules/precompiled headers, and a macOS 13.0 deployment target. It is not a ready-made build for the snapshot in this experiment. Any later build must pin the snapshot Chromium revision, verify its DEPS ANGLE pin, account for any required compatibility patch by hash, and keep the source modifications narrowly scoped.

The checked-in `phase5-unsigned-chromium-u0u1.yml` workflow validates and prepares the official prebuilt snapshot; it does not compile Chromium source changes. Its current ANGLE input default also differs from the snapshot's DEPS pin. Therefore neither existing workflow alone validates a Chromium fallback patch against the desired source. Existing build-preflight records describe a four-CPU, roughly 14-GiB macOS Intel runner, but do not establish that a full Chromium build fits its job budget; they recommend a separate design for a full build, remote execution, or a larger runner. A future build needs an explicitly allocated source/output/cache storage budget that preserves existing evidence, plus a pinned toolchain and enough time for the full target. No build or device acceptance is implied by this research note.

## Focused proposal validation

The exact unmodified `gpu_info_collector.cc` source is identified by its SHA-256 in `tests/phase5-chromium-family1-es2-info-static.py`. Run that focused audit with `--gpu-info-source` pointing to the public file fetched from the pinned revision. It checks patch applicability and compiles the opt-in condition in a small policy harness; the harness covers the complete explicit opt-in, absent or different environment values, and absent or different switches. This is neither compilation of the Chromium translation unit nor app/device acceptance. Browser-to-GPU propagation, command decoder compatibility, full source build, unsigned assembly, first signing, and runtime checks are still required.
