## macOS Keychain and browser profiles

A dedicated Chromium user-data directory separates browser profile files. It does not by itself create a separate macOS Keychain, item ACL, or access group. At the repository's Chrome 156 Chromium pin (`d0c02bfad08ec92a6ffcf989e53cd995e6381a4c`), `kUseKeychainKeyProvider` is enabled by default, and `browser_process_impl.cc` registers the default macOS `KeychainKeyProvider` when that feature is enabled. At the Chrome 158 pin (`b8c2be851f62f6a394ec57955d7f31335d7cb6d4`), both `kUseKeychainKeyProvider` and `kKeychainKeyProviderUserDataDirProtection` are enabled by default. For a non-default user-data directory, `browser_process_impl.cc` registers a temporarily unavailable `v10` provider and a `v11` `KeychainKeyProvider` with a custom salt. This changes the encrypted-data key path, but still uses `KeychainKeyProvider` and `KeychainV2` to access the macOS Keychain. These statements describe those fixed source revisions; feature overrides and other Chromium versions can differ. See the pinned [156 feature default](https://chromium.googlesource.com/chromium/src/+/d0c02bfad08ec92a6ffcf989e53cd995e6381a4c/chrome/common/chrome_features.cc), [156 provider selection](https://chromium.googlesource.com/chromium/src/+/d0c02bfad08ec92a6ffcf989e53cd995e6381a4c/chrome/browser/browser_process_impl.cc), [156 key provider](https://chromium.googlesource.com/chromium/src/+/d0c02bfad08ec92a6ffcf989e53cd995e6381a4c/components/os_crypt/async/browser/keychain_key_provider.mm), [158 feature defaults](https://chromium.googlesource.com/chromium/src/+/b8c2be851f62f6a394ec57955d7f31335d7cb6d4/chrome/common/chrome_features.cc), [158 provider setup](https://chromium.googlesource.com/chromium/src/+/b8c2be851f62f6a394ec57955d7f31335d7cb6d4/chrome/browser/browser_process_impl.cc), [158 key provider](https://chromium.googlesource.com/chromium/src/+/b8c2be851f62f6a394ec57955d7f31335d7cb6d4/components/os_crypt/async/browser/keychain_key_provider.mm), [158 Keychain password lookup](https://chromium.googlesource.com/chromium/src/+/b8c2be851f62f6a394ec57955d7f31335d7cb6d4/components/os_crypt/common/keychain_password_mac.mm), and [158 Keychain API wrapper](https://chromium.googlesource.com/chromium/src/+/b8c2be851f62f6a394ec57955d7f31335d7cb6d4/crypto/apple/keychain_v2.mm).

Code signing helps macOS identify the requesting code. Apple's designated-requirement documentation explains how the signer and signing identifier contribute to code identity and why changing a distribution/signing path can change that identity. Keychain authorization also depends on the particular item, its access-control model, and the keychain implementation; a bundle identifier or Team ID alone does not establish that two requests have identical authorization. When a prompt appears after a re-sign or app change, investigate the exact app and nested-code signatures, designated requirements, version/source pin, requesting process, item and access-control type, and whether the request actually completed. Treat the prompt as evidence of a request, not proof of a specific cause. See [Apple TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements/) and [Apple TN3137](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains).

Apple documents these distinct responses to a Keychain prompt:

- **Allow Once** grants access for that request; a later request can prompt again.
- **Always Allow** permits future retrieval without another prompt for the matching item/app authorization.
- **Deny** prevents retrieval for that request.

A browser process launching by itself does not show that a Keychain operation succeeded. Launching after a denial does not establish successful key retrieval, decryption, or reuse of existing encrypted data. Check those outcomes separately for the exact build and operation; do not infer them from a visible window alone. See [Apple Support's Keychain prompt guide](https://support.apple.com/guide/keychain-access/kyca1243/mac) and [app access controls](https://support.apple.com/guide/mac-help/kychn002/mac).

Keychain models also differ. Apple's TN3137 describes the file-based keychain search list, which can include both a user's login keychain and the shared System keychain, and distinguishes it from the data-protection keychain and its access groups. A separate user profile therefore is not a claim of full Keychain separation. Confirm the relevant keychain type and item scope before interpreting a comparison.

The former handoff examined Chromium revision `82303c21a18acdc256c6264cd2ed0e1588df99d4`. Keep that reference as a fixed-version investigation, not as proof of present behavior or a cause for a different Chrome build. The 156 and 158 source links above are the corresponding repository pins; an unlisted or later version requires its own source check. None of these references establishes what occurred on a particular Mac.

Do not automatically remove or change existing browser data, Keychain items, ACLs, access groups, or security settings. Do not treat a mock provider or a denial as a normal-use procedure. Any Keychain operation or real-browser investigation is owner-managed.
